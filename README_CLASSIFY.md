# 語言模型欄位判斷 - FENTAY B2B CLASSIFY

本文件說明第二種 LLM 用法：**讓語言模型只判斷「這一欄是什麼」**，
不讓它碰資料值。

第一種用法（LLM 逐字生成完整資料）的說明見 [README.md](README.md)。

---

## 結論先行

`FENTAY_B2B_CLASSIFY/` 是一份**尚未接軌到生產流程的規格**。

本文件記錄兩輪實測。**核心問題是：餵給模型多少規格文件才夠？**

### 4 組 arm 比較（qwen3.5:4b，18 個乾淨案例，10 列樣本）

| arm | Prompt 內容 | 完全正確 | 欄位準確率 | prompt tok | 格式違規 |
| --- | ----------- | -------- | ---------- | ---------- | -------- |
| A0 | 僅欄位詞彙清單 | **0/18** | 0.033 | 711 | 7/18 |
| A1 | 僅 MAPPING.md | **1/18** | 0.371 | 2,246 | **8/18** |
| A2 | SKILL.md + MAPPING.md | 10/18 | 0.826 | 3,162 | 3/18 |
| A3 | 三份全讀 | **15/18** | **0.943** | 5,206 | **1/18** |

**只有 A3 能用，A2 是勉強可用的下限。A0 與 A1 皆不可行。**

只看重點：真實 PDF 上 A3 達 **14/15 完全正確、0.993 欄位準確率**。

### 三個關鍵發現

**1. 只給 MAPPING.md 比完全不給規則更糟**

A0 的格式違規 7/18，A1 是 **8/18** —— 多給一份文件反而更差。

原因是**輸出契約寫在 `SKILL.md`，不在 `MAPPING.md`**。契約包含：
mapping 長度必須等於欄位數、欄位名不可重複、只能用 JSON `null` 而非字串 `"null"`。

只給 MAPPING.md，模型會埋頭做內容推理而忘記輸出規範，實測會自創結構
（例如輸出 `{'col_idx': ..., 'db_col': ...}`）或長度不符。

**結論：「只讀 mapping」這個方案不可行。規則給了但契約沒給，模型會發明格式。**

**2. 程式碼取出的表頭餵給模型是有害的**

同一批 PDF 直接比較（無表頭 vs 有表頭，A3）：

| PDF | 無表頭 | 有表頭 | 結果 |
| --- | ------ | ------ | ---- |
| 6B55G | 對 | 對 | 相同 |
| 6B55H | 對 | **錯** | 更差 |
| 6B55J | 對 | 對 | 相同 |

A2 的情況更明顯：2 個變差、1 個變好。**沒有任何一個案例因給表頭而變好。**

根因是 PDF 引擎把相鄰欄位的表頭合併成同一個 span。實測 `訂購單號` 與
`料 號` 被排在同一個 span（x=21），程式碼取表頭時 x=66 那一欄取不到自己的
表頭，會錯抓右側的 `材料名稱/顏色代碼`，導致兩欄拿到相同表頭，模型看到
重複表頭便將其中一欄填 `null`。

**這推翻「把程式碼抽到的表頭給 AI 會幫上忙」的直覺。**

**3. 樣本列數確實有影響（修正早期結論）**

| 樣本列數 | A3 完全正確 | 欄位準確率 |
| -------- | ---------- | ---------- |
| 3 列 | 9/10 | 0.980 |
| 10 列 | **10/10** | **1.000** |

6BGJ9 的 QTY/UNIT 錯位被解決。該檔的 QTY 含 `11,000.0`、`4,850.0` 等大數字，
3 列不足以看出規律。

**注意**：早期在單一 PDF（`豐泰.pdf`）上測得的「1 列就夠」不能推廣到多樣資料。
單一 PDF 的欄位自我說明（`碼` 就是單位、`2026/03/27` 就是日期），
但換成 10 份真實訂單後，樣本數就有鑑別度了。

### 實務建議

- **只用 A3**（三份全讀）。A2 多省 40% tokens，但真實 PDF 上只對 9/15。
- **無論選哪個 arm，都必須加程式碼層的輸出驗證。** A3 在 18 個案例中
  仍有 1 次欄位名重複。規格明文禁止這件事，但模型會犯錯且不會報錯，
  會靜默把兩欄資料寫進同一欄。

**這份規格若要接軌，必須先加程式碼層的輸出驗證。** 詳見
[規格缺陷](#規格缺陷三個實測發現的問題)。

## 兩種 LLM 用法的差異

這是理解本文件的前提。兩種用法性質完全不同：

| 比較項目 | 第一組：LLM 生成完整資料 | 第二組：LLM 只判斷欄位 |
| --- | --- | --- |
| LLM 的任務 | 讀圖 → 逐字輸出所有資料值 | 只回答「這一欄是什麼」 |
| LLM 是否碰資料值 | **是**，必須逐字轉錄 | **否**，只讀樣本判斷語意 |
| 產出 | 完整 JSON（38 筆） | mapping 陣列（10 個欄位名） |
| 規格目錄 | `FENTAY_B2B/` | `FENTAY_B2B_CLASSIFY/` |
| 主程式 | `ollama_fentay.py` | 尚未有（`test_classify_spec.py` 僅為測試） |
| 說明文件 | [README.md](README.md) | 本檔案 |

第一組的結論已定案（純 LLM 生成完整資料不划算，詳見 README）。
第二組的規格存在但未接軌，本文件記錄的是它的**可實作性實測**。

## 規格內容

`FENTAY_B2B_CLASSIFY/` 三份文件：

| 檔案 | 內容 |
| ---- | ---- |
| `SKILL.md` | 任務邊界、輸入輸出契約、欄位詞彙 |
| `MAPPING.md` | 判斷依據：標題別名、內容特徵、消歧規則 |
| `EXAMPLES.md` | 三個範例，含明確的錯誤示範 |

核心契約（`SKILL.md`）：

- 輸入：表格欄位數 N、若干列樣本（格式為「欄位索引=值」）、表頭（選用）
- 輸出：`{"mapping": ["ORD_NO", "MATM_NAME", ..., null, "NEED_CUST"]}`
- 長度必須等於 N，第 i 個元素對應欄位索引 i
- 同一欄位名最多出現一次
- **不含任何資料值**

消歧規則（`MAPPING.md`）分三類，其中數值欄位最具參考價值：

> 乘積關係是對稱的，只能找出金額欄，無法分辨 QTY 與 PRICE。
> 第 2、3 點屬於弱證據，數值大小不可作為依據
> （單價高、數量少的訂單很常見，例如數量 2.0、單價 104.00）。

這段寫得誠實且準確 —— 與實測資料完全吻合（豐泰.pdf 同時有
`820.0 × 73.00` 與 `2.0 × 104.00` 兩種型態）。

## 實測方法

`test_classify_spec.py` 以**三份文件的實際內容**組 prompt（不改寫、不摘要），
餵給本地 Ollama，檢查輸出的 mapping 是否正確。

```powershell
python test_classify_spec.py                    # 全部案例 x 4 組 arm
python test_classify_spec.py --arms A0 A1       # 只比較指定 arm
python test_classify_spec.py --only E           # 只跑某群案例
python test_classify_spec.py --samples 10       # 給模型看幾列樣本
python test_classify_spec.py --model gemma4:12b # 換模型
python test_classify_spec.py --runs 5            # 增加重複次數
python test_classify_spec.py --dump-prompt      # 印出實際 prompt
```

### 4 組 arm 的設計

每組只增加一份文件，用來歸因每份文件的貢獻：

| arm | Prompt 組成 | 設計目的 |
| --- | ----------- | -------- |
| A0 | 欄位詞彙清單（取自 `fentay_common.HEADER_ALIASES` 的鍵）+ 不匯入提示 + 輸出格式要求 | 最低基準，證明「只給欄位名」不夠 |
| A1 | MAPPING.md | 檢驗「只給規則」是否可行 |
| A2 | SKILL.md + MAPPING.md | 加入任務邊界與輸出契約 |
| A3 | 三份全讀 | 加入 few-shot 範例 |

A0 的詞彙清單從程式碼取得而非另外硬編一份，避免兩處不同步。

### 量測指標

| 指標 | 為什麼要量 |
| ---- | ---------- |
| 完全正確率 | 主要指標。靜默錯一欄就會污染資料，比欄位準確率重要 |
| 欄位準確率 | 區分「差一點」與「完全錯」 |
| 格式違規率 | 長度不符 / 欄位名重複 / 使用字串 `"null"` |
| prompt tokens、耗時 | 準度相同時，成本決定選哪個 arm |

### 汙染案例必須排除

`EXAMPLES.md` 內含 3 個範例，而其中 3 個正是測試案例（`case_examples_1/2/3`）。
對 A3 arm 而言這等於開卷考答案。

實測對照（qwen3.5:4b）：

| | 含 EXAMPLES.md | 不含 |
| - | -------------- | ---- |
| 範例1 無表頭 11 欄 | 1.000 | 0.727 |
| 範例2 無表頭 8 欄 | 1.000 | 0.500 |
| 範例3 有表頭 9 欄 | 1.000 | 1.000 |

**含範例時 5/5 拿掉後掉到 2/5。** 文件開頭雖寫了「不可直接沿用範例的 mapping」，
實測模型仍明顯受影響。

因此腳本將案例標記為 `contaminated`，**arm 排名只用乾淨案例**。
本文件的 arm 比較基於 18 個乾淨案例，汙染的 3 個另列參考。

若要把這份 skill 用於生產，必須決定：把 `EXAMPLES.md` 從正式 prompt 移除
（失去 few-shot 效果），或接受它是 few-shot 但用未見過的案例做驗證。

### Ground truth 的來源與可靠性

| 案例類型 | Ground truth | 可靠性 |
| -------- | ------------ | ------ |
| 合成案例（`layout_tests/`） | 產生 PDF 時的設計順序 | 完全可靠，無需人工 |
| 真實 PDF（`PDF/`、`豐泰.pdf`） | `infer_fields()` 推導 | 附獨立交叉驗證 |

真實 PDF 的 ground truth 有一個風險：`infer_fields()` 本身在異常版式下會出錯。
實測以「正確答案已知的合成 PDF」檢查它，錯誤率為 **6.0%**（47/50 欄正確）。

**但這 6% 只發生在欄位順序異常的版式。** 本次 10 份新 PDF 全部是標準版式
（與 `豐泰.pdf` 相同），因此另以 **QTY × PRICE = PDF 金額** 的交叉驗證確認：

| 檢查 | 結果 |
| ---- | ---- |
| 10 份 PDF 欄位推導 | 全部 10 欄正確，來源 L1 表頭虛線 |
| 交叉驗證 | **65/65 筆通過，0 不一致** |

此檢查獨立於 `expected.json`：若欄位錯位，QTY 與 PRICE 會對到不同資料列，
相乘即不會等於該列金額。腳本會把驗證不通過的案例標記為「基準可疑」。

實測中 10 份新 PDF 的 `NEED_CUST` 有 9 種不同值（EW1/FA2/HF/IWe/IWn/IWw/LU2 等），
比 `豐泰.pdf` 的 LU1/DS1 複雜得多，是本次樣本數能有鑑別度的原因之一。

### 4 組 arm 的完整失敗型態

| arm | 失敗型態 |
| --- | -------- |
| A0 | 11 例格式違規（自創 `{'col_idx':..., 'db_col':...}` 結構）、5 例長度不符、1 例 JSON 解析失敗 |
| A1 | 9 例格式違規、5 例長度不符、4 例使用字串 `"null"`、1 例欄位名重複 |
| A2 | 5 例欄位判斷錯誤、2 例欄位名重複、1 例長度不符 |
| A3 | 2 例欄位判斷錯誤、1 例欄位名重複 |

A1 的格式違規比 A0 更多（8 vs 7），這是最反直覺的一點，詳見結論先行第 1 點。

## 實測結果詳錄

### 有表頭：順序不影響判斷

**案例 B1：10 欄完全打亂**

欄位順序刻意排為 `[子公司, 交貨日期, 金額, 單價, 數量, 規格, 料號, 單位, 訂購單號, 材料名稱]`

| 模型 | 得分 | 耗時 |
| ---- | ---- | ---- |
| qwen3.5:4b | **1.000** | 4.6 秒 |
| gemma4:12b | **1.000** | 12.7 秒 |

**MAPPING.md 的「與欄位順序無關」宣稱成立。** 表頭是明確規則，不需推論。

**案例 B2：料號延後到第 5 欄**

訂購單號在第 0 欄、料號在第 5 欄（與常見的「料號在前」相反）。

| 模型 | 得分 | 結果 |
| ---- | ---- | ---- |
| qwen3.5:4b | **0.900**（5/5 次穩定失敗） | 欄位 1 誤判，且欄位名重複 |
| gemma4:12b | **1.000** | 正確 |

qwen 的錯誤輸出：

```
期望: [ORD_NO, MATM_DESC, PRICE, UNIT, WIDE, MATM_NAME, NEED_DATE, QTY, null, NEED_CUST]
實際: [ORD_NO, MATM_NAME, PRICE, UNIT, WIDE, MATM_NAME, NEED_DATE, QTY, null, NEED_CUST]
                 ^^^^^^^^                  ^^^^^^^^
```

兩個問題同時發生：

1. 欄位 1 的 `材料名稱/顏色代碼` 被判成 `MATM_NAME` 而非 `MATM_DESC`
2. **`MATM_NAME` 出現兩次** —— 違反 `SKILL.md` 明文規定

這不是隨機誤差：5 次執行全部產生相同錯誤。

### 無表頭：不可靠

**案例：8 欄順序打亂**

| 模型 | 得分 | 錯誤內容 |
| ---- | ---- | -------- |
| qwen3.5:4b | **0.500** | ORD_NO→MATM_NAME、NEED_CUST→MATM_DESC、WIDE→NEED_DATE |
| gemma4:12b | **0.875** | 僅 ORD_NO→MATM_NAME |

**案例：12 欄完全打亂**（刻意讓數量小、單價高，測試消歧規則）

| 模型 | 得分 | 錯誤內容 |
| ---- | ---- | -------- |
| qwen3.5:4b | **0.667** | ORD_NO/MATM_NAME 位置互換、多填一個 WIDE |
| gemma4:12b | **0.750** | 同上 |

兩個模型都把 ORD_NO 與 MATM_NAME 判錯。這組欄位是
`9800/9801/9802` 對 `6AF9901/6AF9902/6AF9903`，格式上 ORD_NO 明顯
（開頭 6AF），但仍被判錯 —— MAPPING.md 說「格式與表頭文字優先」，
無表頭時這個規則沒有可操作的依據。

### 與真實 PDF 對照

豐泰.pdf 第 1 頁（10 欄、有表頭）：

| 模型 | 得分 | 耗時 |
| ---- | ---- | ---- |
| qwen3.5:4b | **1.000** | 3.7 秒 |
| gemma4:12b | **1.000** | 6.8 秒 |

真實資料反而比人造案例簡單，因為每欄內容自我說明
（`碼` 就是單位、`2026/03/27` 就是日期）。

## 規格缺陷：三個實測發現的問題

### 1. 缺少輸出驗證機制（最嚴重）

`SKILL.md` 第 43 行明文規定「同一個欄位名稱在 mapping 中最多出現一次」，
但模型會違反這條規則。arm 比較的實測證據：

| arm | 格式違規案例數 | 其中「欄位名重複」 |
| --- | -------------- | ----------------- |
| A0 | 7/18 | 0 |
| A1 | 8/18 | 1 |
| A2 | 3/18 | 2 |
| A3 | **1/18** | **1** |

**即使讀了全部三份文件的 A3，仍會產生欄位名重複。**
在「有表頭 料號延後至第5欄」案例中，qwen 以 5/5 次穩定輸出重複的
`MATM_NAME`，且每次都相同（不是隨機誤差）。

**這個錯誤不會報錯**，會靜默把兩欄資料寫進同一個欄位，導致料號被覆蓋，
且沒有任何跡象顯示出錯。

若要接軌，mapping 輸出**必須**經過程式碼驗證：

- 長度是否等於 N
- 欄位名是否重複
- 值是否在允許詞彙內（注意 `"null"` 字串 vs JSON `null`）
- 不確定的欄位是否誠實填 null 而非猜測

不能直接信任 AI 輸出。**這一項在 4 組 arm 中全部成立，包含效果最好的 A3。**

### 2. `null` 的表示形式未定義

實測 qwen 回傳的是字串 `"null"` 而非 JSON `null`：

```json
{"mapping": ["ORD_NO", "MATM_NAME", "WIDE", ..., "null", ...]}
```

A1 arm 出現 4 例此問題。程式碼若用 `if field:` 判斷，會把字串 `"null"`
當成有效欄位名寫進資料庫。規格需明確規定，或在解析時強制正規化。

### 3. 無表頭情境的能力被高估

`MAPPING.md` 第 6-7 行寫「判斷以表頭文字為第一依據…與欄位的排列順序無關」，
這在有表頭時成立。但文件給人的整體印象是「照做就能對」，
而實測顯示無表頭時只有 0.500~0.875。

文件第 61 行自己誠實寫了「第 2、3 點屬於弱證據」—— 這個警覺是對的，
但結論仍容易被誤解。建議在 `SKILL.md` 明文標註：
**無表頭情境不屬於本 Skill 的可靠範圍。**

### 4. 沒有說明「輸出契約放在 SKILL.md 而非 MAPPING.md」

實測最反直覺的結果是 **A1（只給 MAPPING.md）的格式違規率比 A0（完全不給規則）
更高**（8/18 vs 7/18）。

規格把「判斷依據」放在 MAPPING.md、「輸出契約」放在 SKILL.md，
但文件沒有指出這個分工的重要性。讀者若只拿 MAPPING.md 去寫 prompt，
會得到一個規則齊全卻格式崩潰的結果。

建議在 `SKILL.md` 開頭加一句：**本檔案的輸出契約與 MAPPING.md 的判斷規則
必須同時提供，單獨提供任一份都會導致實測可見的失敗。**

## 與程式碼路線的關係

目前 `pdf_text_fentay.py` 的 `infer_fields()` **只會表頭比對**，
完全沒有 MAPPING.md 描述的消歧邏輯（乘積驗算、小數位判斷、重複程度分析）。
無表頭時它依賴 `DOCUMENT_COLUMN_ORDER` 這個固定順序常數（長度 10）。

實測對照（無表頭情境，因為有表頭時程式碼已達 100%）：

| | 程式碼 `infer_fields()` | AI（A3，qwen3.5:4b） |
| - | ----------------------- | --------------------- |
| 無表頭，順序打亂 | 幾乎全錯（靠固定順序猜） | 0.500~0.875 |
| 真實 PDF（10 份，無表頭） | 10/10（但有表頭可用） | **10/10** |
| 耗時 | 0.02 秒 | 4.4 秒 |

**AI 在無表頭情境確實優於現有程式碼**，這是規格的實際價值所在。
但對本次測試的 10 份真實 PDF（有標準表頭），兩者都達 100%，
AI 只多花 4.4 秒與 5,206 tokens。

程式碼路線的完整分析見 [README.md 的路線 C 章節](README.md#路線-c-執行原理)。
