# FENTAY B2B 訂單解析工具

將豐泰（FENTAY）訂購單 PDF 轉換為 `FENTAY_B2B` 資料表格式的 JSON。

本專案實作多條解析路線並提供量化比對，用來評估「要不要用 LLM 來做這件事」。

---

## 文件分組

LLM 在這個專案有兩種**性質完全不同**的用法，兩者不可混為一談：

| | 第一組：LLM 生成完整資料 | 第二組：LLM 只判斷欄位 |
| --- | --- | --- |
| LLM 的任務 | 讀圖 → 逐字輸出所有資料值 | 只回答「這一欄是什麼」 |
| LLM 是否碰資料值 | **是**，必須逐字轉錄 | **否**，只讀樣本判斷語意 |
| 產出 | 完整 JSON（38 筆） | mapping 陣列（10 個欄位名） |
| 規格 | `FENTAY_B2B/` | `FENTAY_B2B_CLASSIFY/` |
| 程式 | `ollama_fentay.py`、`pdf_text_fentay.py` | `test_classify_spec.py` |
| 說明文件 | **本檔案**（[往下看](#快速開始)） | **[README_CLASSIFY.md](README_CLASSIFY.md)** |

**怎麼選：**

- 想了解「整份資料交給 LLM 做」的完整評估 → 看本檔案
- 想了解「只讓 LLM 判斷欄位語意」的規格與實測 → 看
  [README_CLASSIFY.md](README_CLASSIFY.md)

第一組的結論已定案（純 LLM 不划算），第二組的規格仍**未接軌到生產流程**，
兩者的成熟度不同。

## 檔案結構

```
fentay_common.py       規則的唯一實作（MAPPING.md 轉換規則 + 輸出契約）
├── ollama_fentay.py   路線 B：PDF → PNG → vision 模型 → JSON
└── pdf_text_fentay.py 路線 C：PDF 文字層 → 座標分組 → JSON

test_fentay.py         單元測試
compare_results.py     批次比較所有 result.*.json
ai_locate_experiment.py 實驗：AI 能否取代程式碼做版面定位
check_env.py           環境檢查
expected.json          38 筆基準答案
run.bat                功能選單（雙擊執行）
make_layout_pdfs.py    產生欄位順序可控的測試 PDF

FENTAY_B2B/            第一組規格：LLM 生成完整資料
FENTAY_B2B_CLASSIFY/   第二組規格：LLM 只判斷欄位
README_CLASSIFY.md     第二組的說明與實測結果
```

`fentay_common.py` 是關鍵設計：轉換規則只有一份實作，各路線共用，
因此比對結果才具有可比性。它只依賴 Python 標準函式庫，不需要 `fitz` 或 `requests`。

## 兩條解析路線

|          | 路線 B（vision） | 路線 C（文字層） |
| -------- | ---------------- | ---------------- |
| 原理     | PDF 渲染成 PNG 餵給 vision 模型 | 直接讀 PDF 文字層 |
| 耗時     | 約 115 秒 / 2 頁 | **約 0.02 秒 / 2 頁** |
| 外部依賴 | Ollama（16 GB 模型常駐） | 無 |
| 掃描件   | 可處理 | **失效**（會明確報錯） |
| 版面容忍 | 較高 | 較低（依賴表頭虛線定位欄位） |

### 兩種工作模式：`pure` 與 `hybrid`

路線 B 有兩種模式，差別在於 **MAPPING.md 的轉換規則由誰執行**。

```
pure 模式（全部交給模型）
  PDF ──渲染──> PNG ──> vision 模型 ──讀圖 + 套用全部規則──> 最終 JSON
                                        │
                                        └─ 單位 碼→YD
                                           日期 2026/03/27→20260327
                                           金額 略過
                                           BRAND_NO 等三欄補空字串

hybrid 模式（模型只讀表，規則交給程式）
  PDF ──渲染──> PNG ──> vision 模型 ──只讀表格──> 原始值 + 原始欄位名
                                        │
                     ┌──────────────────┘
                     ▼
              fentay_common.py ──套用同一份規則──> 最終 JSON
```

`pure` 模式的用途是**測試 Skill 本身的指令是否有效** — 把 `SKILL.md`、
`MAPPING.md`、`EXAMPLES.md` 全文塞進 prompt，看模型能不能照做。
這是評估「這個 Skill 寫得好不好」的方法。

`hybrid` 模式則是**實務做法** — 模型只負責它擅長的讀圖，
規則交給確定性的程式碼執行。

### 實測結果（`豐泰.pdf`，2 頁共 38 筆）

| 組合 | 筆數 | 欄位正確率 | 耗時 |
| ---- | ---- | ---------- | ---- |
| 路線 C | 38/38 | 100.0% | 0.02 秒 |
| 路線 B `qwen3.5:4b` hybrid | 38/38 | **99.8%** | 116 秒 |
| 路線 B `qwen3.5:4b` pure | 38/38 | 89.9% | 122 秒 |
| 路線 B `gemma4:12b` hybrid | 35 | 75.5% | 441 秒 |
| 路線 B `gemma4:12b` pure | 36 | 73.6% | 505 秒 |

輸入法為 `temperature=0`，但小模型在視覺辨識上仍非確定性輸出，
同一組合重跑的正確率會有數個百分點波動。上表為最近一次執行結果。

#### hybrid 模式剩下的 1 處錯誤

```
6AF1122  預期='44" 黑保利2 CDP布/(00A)'  實際='44"黑保利2 CDP布/(00A)'
```

材料名稱中漏掉一個空格。原文的空格本身沒規律（38 筆中 3 筆在寬度後有空格、
28 筆沒有），因此**沒有任何內部一致性訊號可用來判斷空格是否遺失**，
只能靠 OCR 本身。目前無解。

## OCR 失真修正：色碼 O/0 混淆

vision 模型在低解析度下會把數字 `0` 認成字母 `O`：

```
6AF1105  0AVLJA4497K9EPM5回網/(0AV)  →  OAVLJA4497K9EPM5回網/(0AV)
6AF1112  0BG A2279-2EPM5保利2/(0BG)  →  OBG A2279-2EPM5保利2/(0BG)
```

**成因**：豐泰訂單為 8pt 中文字，200 DPI 下字高僅約 22px，
在 MingLiU 明體字型中數字 `0`（窄橢圓）與字母 `O`（方圓）幾乎無法區分。

**解法**：`fentay_common.py` 的 `fix_ocr_color_code()` 自我一致性檢查。
豐泰的材料名稱常以色碼開頭，且尾端括號會重複該色碼：

```
0AVLJA4497K9EPM5回網/(0AV)
└─ 前綴 ─┘      └ 括號 ┘
```

當兩者只有首字元 `O`/`0` 之差時，以括號內的數字 `0` 為準修正。
規則嚴格（要求後兩個字母完全相同），對正常資料為 no-op。

實測效果：3/3 執行皆修正 2 筆，正確率從 99.3% 提升至 **99.8%**。
對 `expected.json`、路線 C 結果、`gemma4` 結果皆為 0 影響。

## 關於 DPI：不要盲目提高

實測發現 **Ollama 服務端對視覺 token 數有上限**（約 4,049 tokens，
即約 4,150,000 px）。超過上限的圖片會被降解析度，因此
**提高 DPI 不等於提高模型看到的清晰度**：

| 設定 DPI | 實際像素 | 視覺 token | 是否被壓縮 | **實際有效 DPI** |
| --- | --- | --- | --- | --- |
| 150 | 1.59M | 1,577 | 否 | 150 |
| **200（預設）** | 2.82M | 2,773 | 否 | **200** |
| 300 | 6.34M | 4,049 | 是 | ~196 |
| 400 | 11.27M | 4,049 | 是 | **~148（比 200 更差）** |

實測（`qwen3.5:4b` hybrid，各跑 3 次）：

| DPI | MATM_DESC 錯誤 | 整體 | 備註 |
| --- | --- | --- | --- |
| **200** | 1 / 1 / 1 | **99.8%** | 穩定 |
| 400 | 2 / 2 / 2 | 99.6% | 反而變差 |
| 240 | 1 + 5 次失敗 | — | Ollama 行程崩潰（記憶體耗盡） |

400 DPI 變差的原因是：模型把 `0BG` 的**兩處**都讀成 `OBG`，
內部一致，修正規則偵測不到。

**300 DPI 以上在 31.5 GB RAM 的機器上曾導致 Ollama 行程崩潰。**
若要提高 DPI，請先確認記憶體充足並觀察穩定性。

#### `pure` vs `hybrid` 的差距來自哪裡

以 `qwen3.5:4b` 為例，`hybrid` 比 `pure` 高 9.4 個百分點，逐欄看：

| 欄位 | pure | hybrid |
| ---- | ---- | ------ |
| `NEED_DATE` | **0.0%** | 100.0% |
| `PRICE` | 92.1% | 100.0% |
| `BRAND_NO` / `CUST_NO` / `CONTACT_NO` | **整欄消失** | 100.0% |

- **`NEED_DATE`**：38/38 筆原樣輸出 `2026/03/27`，完全沒套用「去除斜線」規則
- **`BRAND_NO` 等三欄**：38 筆全部沒有這三個欄位，觸發 38 個驗證問題。
  SKILL.md 的輸出格式範例有列出，模型還是漏掉
- **`PRICE`**：3 筆把 `9.30` 誤讀成 `9.33`

**結論：寫在 prompt 裡的規則對 4B 模型不可靠。**
只要規則是明確的轉換（單位、日期、小數位、預設值），
就應該實作在程式碼裡，不要交給模型。

#### 路線 B vs 路線 C 的差距

加上 OCR 修正規則後只剩 **1 格**，全部在 `MATM_DESC`：

```
6AF1122  44" 黑保利2 CDP布/(00A)   vs  44"黑保利2 CDP布/(00A)
```

修正規則啟用前是 3 格，其中 2 格為數字 `0` 被認成字母 `O`（已修正）。
剩下這 1 格是空格遺失，**無解** — 原文空格本身沒規律，沒有內部訊號可判斷。

這類失真發生在讀圖階段，規則套用是在之後，因此
**再增加多少轉換規則都無法彌補**。要根治只能提升 OCR 品質，
但實測提高 DPI 反而更差（見「關於 DPI」章節）。

### 建議

**若 PDF 都有文字層，以路線 C 為主力，路線 B 留給掃描件。**
路線 C 在速度與準確度上都勝出（100% vs 99.8%，0.02 秒 vs 116 秒），
且不依賴任何模型。

若只能用路線 B，務必用 `hybrid` 模式而非 `pure`。

**兩件事都不建議交給 AI：**

- **座標偵測** —— 實測 AI 要求輸出欄位邊界時會直接崩盤，
  把輸入的所有 x 值原封不動倒出來（見「AI 版面定位實驗」）。
- **欄位語意判斷** —— AI 雖能做到 100%，但確定性方法同樣是 100% 且快 200 倍，
  導入 AI 只有延遲成本。

換言之，AI 在這條流水線上目前**沒有可貢獻的環節**。

## 關於 `expected.json` 的循環比對

`expected.json` 是用**路線 C 的方法**產生的，所以路線 C 與它比對必然是 100%，
這**不能**作為路線 C 正確的證據。

因此 C 額外提供獨立的交叉驗證：

```
QTY x PRICE ≈ 該列的「金額」
```

此檢查不依賴 `expected.json`。若欄位歸屬錯位，QTY 與 PRICE 會對到不同資料列，
相乘就不會等於該列金額，因此能有效偵測錯位。實測 38/38 通過。

路線 B 與 `expected.json` 的比對則是有效的，因為兩者走完全不同的擷取路徑。

## 路線 C 執行原理

`pdf_text_fentay.py` 為什麼能達到 100%，以及它到底怎麼取得資料位置。

### 這不是 OCR

路線 C **不做 OCR**，而是直接讀 PDF 內嵌的「文字層」。

PDF 裡的文字不是圖片，而是儲存了每個字元的**座標**。例如 `6AF1101`
在檔案中的記錄是「x=21, y=107 開始的一串字元」。PyMuPDF 讀出來如下：

```
y=38    x=82    '隆芳興業股份有限公司'
y=38    x=21    '致  供應商:'
y=51    x=528   '2026/03/20'
```

**位置本來就在檔案裡，不需要推算。** 這與路線 B 相反 — 路線 B 把 PDF
畫成圖片丟給模型，位置資訊在轉圖當下就全部消失，必須靠模型「看」出來。

### 關鍵難題：文字輸出順序是「整欄」不是「逐列」

直接呼叫 `page.get_text()`，輸出順序是：

```
LU1                    ← 所有「需求子公司」連續輸出
LU1
DS1
...
6AF1101                ← 所有「訂購單號」連續輸出
6AF1102
...
3056G                  ← 所有「料號」
44"74F黃LJ-A8-P網布/(74F)   ← 所有「材料名稱」
820.0                  ← 所有「數量」
碼                     ← 所有「單位」
73.00                  ← 所有「單價」
2026/03/27             ← 所有「交貨日期」
59,860.00              ← 所有「金額」
44"                    ← 所有「規格」← 最後才出現，位置在頁尾之後
```

**PDF 的文字層是「按欄儲存」的，不是「按列」。** 順序讀下去只會得到
一堆各自獨立的欄位串，無法知道哪個料號配哪個數量。

因此必須完全忽略文字的先後順序，改用座標。

### 執行流程（六步）

以下數據皆為 `豐泰.pdf` 第 1 頁的實測輸出。

#### 步驟 1：`collect_spans()` — 取出所有文字方塊

```python
spans.append((round(span["bbox"][1]), round(span["bbox"][0]), text))
#                     ↑ y 座標（文字頂端）        ↑ x 座標（文字左緣）
```

第 1 頁共 **263 個 span**，每個都是 `(y, x, 文字)`。

#### 步驟 2：`find_table_bounds()` — 切出表格區域

整頁包含頁首地址、頁尾備註，必須先切掉。

```
資料區 y 範圍: 107 ~ 641 pt  (頁高 806 pt)
保留的 span: 210 / 263
```

- **上界** `y=107`：找 `x < 30` 且文字開頭是數字的 span，取最小 y
- **下界** `y=641`：頁尾長虛線分隔線（111 個 `-`）位於 `y=644`，減 3 作緩衝

#### 步驟 3：`detect_columns()` — 找出每一欄的左邊界

這是「取得正確欄位位置」的核心。三層策略：

**第 1 層（實測採用）：表頭虛線的 x 座標**

表頭下方那排虛線，**每一段的起點就是該欄的左邊界**：

```
y=94  x=21   '--------'                    訂購單號欄
y=94  x=66   '-----'                       料號欄
y=94  x=96   '--------------------------'  材料名稱欄
y=95  x=232  '----------'                  規格欄
y=94  x=288  '-----------'                 數量欄
y=94  x=349  '----'                        單位欄
y=94  x=373  '----------'                  單價欄
y=94  x=429  '--------------'              金額欄
y=94  x=503  '----------'                  交貨日期欄
y=94  x=556  '------'                      需求子公司欄
```

得出 `lefts = [21, 66, 96, 232, 288, 349, 373, 429, 503, 556]`

若其他供應商不用虛線，會退到第 2 層（表頭文字的 x 座標），
再不行退到第 3 層（資料 x 座標分群，此時欄位語意不可靠，程式會發警告）。

#### 步驟 4：`cluster_rows()` — 用 y 座標分組成列

同一列的 span，y 值可能差 1pt；不同列之間相隔 25pt。因此用 **±2pt 容差**：

```
第 1 列: [(21,'6AF1101'), (66,'3056G'), (96,'44"74F黃LJ-A8-P網布/(74F)'),
          (232,'44"'), (313,'820.0'), (350,'碼'), (394,'73.00'),
          (449,'59,860.00'), (503,'2026/03/27'), (565,'LU1')]

第 2 列: [(21,'6AF1102'), (66,'307LJ'), (96,'44"0AH灰LJ-B4網布/(0AH)'),
          (232,'44"'), (318,'54.0'), (350,'碼'), (394,'29.00'),
          (454,'1,566.00'), (503,'2026/03/27'), (565,'LU1')]
```

第 1 頁共 **21 列**，第 2 頁 17 列。

#### 步驟 5：`infer_fields()` — 欄位索引對應到資料庫欄位名

依 MAPPING.md「以標題文字比對為主，與欄位順序無關」，**用表頭文字比對**，
不是靠位置硬編碼：

```
x=21    -> ORD_NO       （比對到「訂購單號」）
x=66    -> MATM_NAME    （比對到「料 號」）
x=96    -> MATM_DESC    （比對到「材料名稱/顏色代碼」）
x=232   -> WIDE         （比對到「規    格」）
x=288   -> QTY          （比對到「數     量」）
x=349   -> UNIT         （比對到「單位」）
x=373   -> PRICE        （比對到「單     價」）
x=429   -> None         （比對到「金      額」，依 MAPPING.md 不匯入）
x=503   -> NEED_DATE    （比對到「交貨日期」）
x=556   -> NEED_CUST    （比對到「子公司」）
```

有兩個非顯而易見的處理：

**(a) 合併 span。** 這份 PDF 把「訂購單號」和「料號」排在**同一個 span** 裡：

```
y=89  x=21  '訂購單號料 號'
```

所以 `header_field_candidates()` 從這一個字串抽出**兩個**別名
`['ORD_NO', 'MATM_NAME']`。距離最近的 `ORD_NO`（距離 0）佔用欄位 0，
落選的 `MATM_NAME` 再填入右側相鄰的未配對欄位（欄位 1）。

**(b) 必須取「最近」的左界，不能取「第一個在容差內的」。**
`材料名稱/顏色代碼` 的 x=102：

```
|102 - 96| = 6    ← lefts[2]=96  正確
|102 - 66| = 36   ← lefts[1]=66  錯誤
```

若用「第一個落在 40pt 容差內的」會抓到 66，欄位整個錯位。

#### 步驟 6：組裝 + 套用規則

```python
raw.setdefault(column_index(lefts, x), []).append(text)
# ↓
row = {欄位名: 值}      # 例如 {"ORD_NO": "6AF1101", "QTY": "820.0", ...}
# ↓
apply_mapping(row)     # 套用 fentay_common 的 MAPPING.md 規則
```

同一欄可能有多個 span（例如長文字被切成數段），用 `""` join 起來。

### 關鍵設計：`column_index()` 用「≤」而非「最近」

```python
def column_index(lefts, x):
    idx = 0
    for i, left in enumerate(lefts):
        if x >= left:      # ← 這裡用 <= 語意
            idx = i
        else:
            break
    return idx
```

理由是**數字欄靠右對齊**，同一欄的 x 座標會隨位數漂移。實測：

| x | 該 x 實際的值 | 應屬欄位 |
|---|---|---|
| 303 | `1,460.0` | QTY |
| 313 | `820.0` | QTY |
| 318 | `54.0` | QTY |
| 323 | `2.0` | QTY |

四個 x 都是 QTY 欄。若用「找最近的左界」：

```
x=323 → 距離 lefts[4]=288 是 35
        距離 lefts[5]=349 是 26  ← 比較近！
        → 會被誤判成 UNIT 欄
```

PRICE 欄（x=389/394/399）與金額欄（x=444/449/454/464）都有同樣情況。
用「小於等於 x 的最大左界」就不會出錯，因為這些值都落在相鄰兩條左界之間。

### 為什麼能做到 100%

因為**文字層就是原始碼，沒有第二層的轉換**。字元從 PDF 移進字串，
中間沒有任何推論或識別。

唯一的風險是「欄位歸屬或列分組錯了」。這由前述的獨立交叉驗證
（`QTY × PRICE ≈ 金額`）抓出。實測 38/38 通過 — 456 格資料要全部對齊，
機率上不可能巧合。

### 路線 C 的已知限制

| 限制 | 說明 |
| ---- | ---- |
| **必須有文字層** | 掃描件完全失效。程式會明確報錯（`[error] 第 N 頁找不到訂單資料`）而非靜默回傳空結果 |
| **第 1 層依賴表頭虛線** | 其他供應商若用框線或無線，會退到第 2/3 層。備援邏輯已實作但**未在真實資料上測試過** |
| **訂單號前綴硬編碼為 `6`** | `find_table_bounds()` 以 `t[:1] == "6"` 找資料區起點（豐泰訂單號為 `6AFxxxx`）。其他前綴會落到較寬鬆的備援條件 |
| **`HEADER_X_TOLERANCE = 40`** | 表頭文字與欄位左界的最大容許距離，此值為經驗設定，本文件剛好適用 |
| **僅測過這份 PDF** | 單一供應商、繁體中文、無框線表單 |

換版式時先跑 `--dump-columns` 確認欄位偵測結果：

```powershell
python pdf_text_fentay.py --pdf ".\豐泰.pdf" --dump-columns
```

## AI 版面定位實驗

`ai_locate_experiment.py` 用來回答一個問題：**這件事能不能改用 AI 做版面定位？**

> **結論先行**
>
> 實驗證明 AI 能把表格欄位命名對（100%，3 次執行完全一致），
> 但**這個專案不需要它** —— `pdf_text_fentay` 的確定性方法已達同等準確率，
> 且快 200 倍。
>
> 本章的價值在於**量測 AI 能力**（「決策可靠、座標不可靠」），
> **不是**提出生產方案。請勿把下文的 100% 誤解為「建議改用 AI」。
>
> 若你只想看「LLM 只判斷欄位」這第二組用法及其規格，請看
> [README_CLASSIFY.md](README_CLASSIFY.md)。

### 實驗 3：給內容，判斷語意（AI 唯一做對的部分）

程式碼用座標把表格分組成「列」與「欄」之後，每一欄的**值**就都有了。
這時把幾列樣本交給 AI，讓它判斷每欄代表哪個資料庫欄位：

```
R0: 0=6AF1101 | 1=3056G | 2=44"74F黃LJ-A8-P網布/(74F) | 3=44" | 4=820.0 | 5=碼 | 6=73.00 | 7=59,860.00 | 8=2026/03/27 | 9=LU1
R1: 6AF1102 | 1=307LJ | 2=44"0AH灰LJ-B4網布/(0AH) | 3=44" | 4=54.0  | 5=碼 | 6=29.00 | 7=1,566.00  | 8=2026/03/27 | 9=LU1
R2: 6AF1103 | 1=309QS | 2=40"10A LJA8P網水性漿/(10A) | 3=40" | 4=2.0   | 5=碼 | 6=104.00 | 7=208.00   | 8=2026/04/10 | 9=DS1
```

AI 回傳：

```json
{"mapping": ["ORD_NO", "MATM_NAME", "MATM_DESC", "WIDE", "QTY",
             "UNIT", "PRICE", null, "NEED_DATE", "NEED_CUST"]}
```

**10/10 欄全對，3 次執行回應完全相同**，包含正確判斷第 7 欄（金額）
不該匯入資料庫而填 `null`。

| 指標 | 數值 |
| ---- | ---- |
| 平均得分 | **1.000**（10/10 欄位） |
| 答案一致性 | 3/3 完全相同 |
| 平均耗時 | 4.0 秒 |
| prompt tokens | 574 |
| 輸出 tokens | 61 |

### 樣本數要給幾列？實測結果是 1 列就夠

這個問題值得單獨驗證，因為「多給樣本應該更準」是直覺上合理的假設。
實測結果（`qwen3.5:4b`，每組 3 次）：

| 樣本數 | 得分 | 3 次一致 | 耗時 | prompt tokens |
| ------ | ---- | -------- | ---- | ------------- |
| 1 列 | **1.00** | 是 | 4.9s | 361 |
| 2 列 | **1.00** | 是 | 3.9s | 464 |
| 3 列（本實驗使用） | **1.00** | 是 | 3.9s | 566 |
| 5 列 | **1.00** | 是 | 4.0s | 780 |
| 10 列 | **1.00** | 是 | 4.1s | 1310 |
| 全部 21 列 | **1.00** | 是 | 4.4s | 2505 |

**1 列就夠了，全部 21 列不會更好。**

原因不是模型聰明，而是這張表的每欄內容**自我說明** ——
`6AF1101` 一看就是單號、`碼` 就是單位、`2026/03/27` 就是日期。
給多少列都是在問同一個已經寫在資料裡的答案。

耗時幾乎不變（3.9–4.9 秒），因為瓶頸是模型載入與思考，不是 prompt 長度。
給全部 21 列只是多燒 2144 tokens 換零收益。

因此**這個實驗的樣本數對「結果正確率」毫無鑑別度**，
3 列並非某種刻意選擇，只是無差別。
這也表示：此實驗無法用來論證「給 AI 多少樣本才夠」這個一般性問題。

### 但這 100% 不能與 Route B 的 99.8% 相提並論

兩者都用「mapping」這個詞，但處於流程的不同位置。**決定性差異是
「AI 有沒有碰過 PDF 的文字」**：

| | Route B hybrid | 實驗 3 |
| --- | ------------- | ------ |
| AI 看到 | 圖片像素（200 DPI PNG） | 程式碼已抓好的文字 |
| AI 輸出 | 380 個字元值（9,146 bytes） | 10 個欄位名（118 bytes） |
| 誰決定哪些字元屬於哪列哪欄 | **AI**（看圖時順帶決定） | 程式碼（座標分組） |
| 量測分母 | 456 格（38 筆 × 12 欄） | 10 個欄位對應 |
| 可能犯的錯 | 認錯字、漏空格、欄位錯位 | 只有欄位語意錯 |
| 實測錯誤 | `44" 黑保利2` → `44"黑保利2` | 無 |

Route B hybrid 的 prompt 明確要求 AI 輸出「**圖片上的原始文字**」，
所以它的 99.8% 是在真實 OCR 任務上量測的。
實驗 3 的 AI 輸出**零個內容值**，因此它的任務**結構上不可能有 OCR 錯誤**。

**99.8% 與 100% 不是同一個尺度上的比較。** 一個是讀 PDF 的完整任務，
一個只是替已經讀好的資料貼標籤。

### 更關鍵：AI 在這個位置是冗餘的

把實驗 3 的結果與 `pdf_text_fentay` 的 `infer_fields()` 併排看：

```
程式碼 infer_fields          AI 實驗 3
  x=21  -> ORD_NO              ORD_NO
  x=66  -> MATM_NAME           MATM_NAME
  x=96  -> MATM_DESC           MATM_DESC
  x=232 -> WIDE                WIDE
  x=288 -> QTY                 QTY
  x=349 -> UNIT                UNIT
  x=373 -> PRICE               PRICE
  x=429 -> None（金額略過）     null
  x=503 -> NEED_DATE           NEED_DATE
  x=556 -> NEED_CUST           NEED_CUST
```

**結果完全相同。** 程式碼 0.02 秒拿到與 AI 4.0 秒相同的答案。

同理，實驗 5 的「100%、38/38 筆」也**不能**當作 AI 混合方案可行的證據 ——
那份 100% 的文字擷取是程式碼做的，AI 只貢獻了已經被程式碼做對的欄位對應。

所以正確的結論不是「可以分工給 AI」，而是「**這個位置不需要 AI**」。
加上去只會多花 4 秒換到同一個答案。

AI 版面定位唯一可能有價值的情境，是 `infer_fields()` 失效時作為備援
（例如供應商更換、表頭被破壞）。但該情境**尚未測試**，
且 `detect_columns()` 已有 L2/L3 備援機制。

### 為什麼這個任務 AI 做得好

因為判斷語意有**明確的線索**，AI 不需要猜：

| 欄 | 內容線索 | 判斷 |
|---|---|---|
| `0=6AF1101` | 格式固定的英數字串，每列遞增 | 訂購單號 |
| `1=3056G` | 短碼英數字串 | 料號 |
| `3=44"` | 帶英寸引號的數字 | 規格寬度 |
| `4=820.0` | 千分位小數 | 數量 |
| `5=碼` | 中文單位詞 | 單位 |
| `7=59,860.00` | 千分位金額，且等於數量×單價 | 金額（不匯入） |
| `8=2026/03/27` | 西元日期格式 | 交貨日期 |

AI 是從**內容**推出語意，不是從位置猜。每一欄的內容都自帶足夠線索。

### Prompt 結構

四個部分，缺一不可：

```
① 幾列樣本（只給值，不給任何座標）

② 可用欄位詞彙（明確指定用左側英文字串）
   ORD_NO=訂購單號, MATM_NAME=料號, MATM_DESC=材料名稱/顏色代碼,
   WIDE=規格寬度, QTY=數量, UNIT=單位, PRICE=單價,
   NEED_DATE=交貨日期, NEED_CUST=需求子公司

③ 格式規格：mapping 必須與欄位索引等長（10 個元素），
   不匯入的欄填 null

④ 具體範例（10 欄的完整輸出）
```

**第 ④ 項是關鍵。** 最初沒有給範例，格式寫成：

```
{"mapping": [<欄位索引0>, <欄位索引1>, ...]}
```

AI 把 `[<欄位索引0>...]` 理解成「要匯入的欄位索引」，回傳了
`[0,1,2,3,4,5,6,8,9]` — 跳過第 7 欄。改成給完整範例後立即正確。

這是實驗過程中最實際的教訓：**沒有明確範例時，測到的會是寫 prompt 的
能力，不是模型的能力。**

### 評分方式

`score_mapping()` 對每個欄位做兩種比對：

- **嚴格比對**：AI 回傳的字串與正確答案完全相符
- **正規化比對**：用 `resolve_field()` 正規化後相符

`resolve_field()` 很重要 —— 它先檢查是否已是合法欄位名（AI 通常直接回傳
`ORD_NO`），再退回 `map_header_to_field()` 做標題比對。
若誤用後者，`ORD_NO` 會被正規化成 `None`，把正確答案判成錯誤。

### 理論上可行的分工，但實務上沒必要

```
程式碼  →  用座標分組，找出列與欄的邊界      0.02 秒，精確
AI      →  只判斷每個欄位的語意              4.0 秒，完美
程式碼  →  依 AI 的判斷套用 MAPPING.md 規則   0.02 秒
```

這個分工在技術上可行 —— 把座標交給程式碼（精確且快），語意交給 AI
（準確），兩者優勢互補。實驗 5 也跑通了這條路徑，得到
**欄位正確率 100%，38/38 筆**。

**但這條路徑沒有價值。** 因為被 AI 取代的那一步（`infer_fields()`）
本來就是 100% 正確且只需 0.02 秒。導入 AI 只是：

- 準確率：0% → 0%（不變）
- 耗時：0.02 秒 → 4.02 秒（多 200 倍）
- 複雜度：多一個 prompt、輸出解析、失敗處理、跨版本行為差異

實驗 5 的 100% 也不是 AI 的功勞 —— 文字擷取是程式碼做的，
AI 只貢獻了程式碼已經做對的欄位對應。

**唯一可能值得考慮 AI 的情境**是 `infer_fields()` 失效時（例如供應商更換、
表頭被破壞），此時 AI 可作為備援。但該情境尚未測試，
且 `detect_columns()` 已有 L2/L3 備援機制。因此目前不建議導入。

### 不可行的任務：輸出座標

同一個實驗也測了四個座標型任務，結果都不理想：

| 任務 | 得分 | AI 的行為 |
| ---- | ---- | --------- |
| 欄位 x 左界 | 0.000 | **把輸入的所有 x 值原封不動倒出來**（24 個值，正確 10 個） |
| 資料區 y 邊界 | 0.300 | 給出 `top=87, bottom=591`（正確 107 / 641），方向對但精度不足 |
| 資料列索引範圍 | 0.744 | 框到 22 列（正確 21 列），命中 16 列 |

欄位邊界那項的失敗型態最能說明問題：AI **沒有理解任務**，直接把輸入
當輸出。座標型任務對 LLM 不可靠。

### 實驗限制

- 實驗 1、2、4 只用了第 1 頁樣本

屆時 `infer_fields()` 可能失效，可以量測 AI 是否能救回來。
在那之前，它只是一份 AI 能力量測紀錄。

## 轉換規則摘要

實作於 `fentay_common.py`，對應 `FENTAY_B2B/MAPPING.md`：

| 欄位 | 來源欄位 | 規則 |
| ---- | -------- | ---- |
| `ORD_NO` | 訂購單號 | 直接填入 |
| `MATM_NAME` | 料號 | 直接填入 |
| `MATM_DESC` | 材料名稱/顏色代碼 | **保留原始字串（含雙引號）** |
| `WIDE` | 規格 | **去除雙引號僅留數字**（`44"` → `44`） |
| `QTY` | 數量 | 去千分位，小數 2 位 |
| `UNIT` | 單位 | `碼`→`YD`、`公尺`→`M`、`公斤`→`KG`、`個`→`PC` |
| `PRICE` | 單價 | 去千分位，小數 3 位 |
| `NEED_DATE` | 交貨日期 | 轉 `YYYYMMDD`，民國年 +1911 |
| `NEED_CUST` | 需求子公司 | 直接填入 |
| `BRAND_NO` / `CUST_NO` / `CONTACT_NO` | — | 固定空字串 |
| （不匯入） | 金額 | 略過 |

`WIDE` 去引號但 `MATM_DESC` 保留引號，這兩者行為不同，
是刻意的設計而非不一致。兩者皆有單元測試鎖定。

```json
}
```

時間為台灣時區（UTC+8）。`_meta` 放在獨立區塊而非頂層，
是為了不影響既有的 `{success, recordCount, data}` 結構，
下游取用 `data` 的程式碼無需修改。

報告檔（`.report.txt`）開頭也記錄產出時間、開始時間與耗時。
檔名格式為 `result.<來源>.<YYYYMMDD-HHMMSS>.report.txt`。

用 `--out-dir` 可改變輸出位置；`pdf_text_fentay.py --report` 可指定報告檔路徑。

## 已知限制

路線 C 的限制（文字層、虛線依賴、`6` 前綴硬編碼等）見
[路線 C 執行原理](#路線-c-執行原理) 一節末的表格。以下為跨路線的限制：

1. **僅測過這一份 PDF、這個供應商、繁體中文。** 跨頁表格、框線、
   民國日期等情境未測試。
2. **`gemma4:12b` 不建議用於本任務。** 參數量比 `qwen3.5:4b` 大三倍，
   但欄位正確率低 24 個百分點，且會幻覺出不存在的訂單號。
3. **`pure` 模式會違反 Skill 規則。** 實測 `NEED_DATE` 正確率為 0%
   （未轉換格式）、`BRAND_NO`/`CUST_NO`/`CONTACT_NO` 整欄消失。
   規則寫在 prompt 裡對小模型不可靠，應實作在程式碼中（用 `hybrid`）。
4. **`PRICE` 的小數位在 JSON 中不會保留。** `73.000` 會變成 `73.0`，
   JSON number 無位數語意。若下游需要 `NUMBER(10,3)` 的固定補位需另行處理。
5. **模型輸出非確定性。** 即使 `temperature=0`，小模型在視覺辨識上
   仍有數個百分點的波動（`pure` 模式曾出現 89.9% 與 93.6% 兩次結果）。
   不應把單次執行結果當成模型的穩定能力指標。
6. **提高 DPI 有風險。** 300 DPI 以上在 31.5 GB RAM 的機器上曾導致
   Ollama 行程崩潰（記憶體耗盡），詳見「關於 DPI」章節。
7. **`FENTAY_B2B_CLASSIFY/` 尚未接軌。** 這是第二組用法（LLM 只判斷欄位），
   目前沒有任何程式碼引用該目錄，`test_classify_spec.py` 僅作測試用途。
   實測結果與已知缺陷見 [README_CLASSIFY.md](README_CLASSIFY.md)。

## 兩種 LLM 用法的成熟度

| | 第一組（本文件） | 第二組 |
| - | ---------------- | ------ |
| 用法 | LLM 生成完整資料 | LLM 只判斷欄位 |
| 規格 | `FENTAY_B2B/` | `FENTAY_B2B_CLASSIFY/` |
| 程式 | `ollama_fentay.py`、`pdf_text_fentay.py` | 尚未接軌 |
| 實測 | 已完成，結論明確 | 已完成可實作性測試，結論待決 |
| 結論 | **不建議用 LLM 生成完整資料** | 有價值但需先加輸出驗證 |

第二組的價值在無表頭情境（AI 0.500~0.875 vs 程式碼幾乎全錯），
但有表頭時 AI 與程式碼同為 1.000，且 AI 慢 200 倍。
詳見 [README_CLASSIFY.md](README_CLASSIFY.md)。
